# 三国杀规则集

> 面向《三国杀》规则的知识表示、冲突分析与可解释推演项目。

**项目阶段：** V0.1 · 初始化  
**技术栈：** 规则建模与推演技术栈尚未确定；现有 Python 环境仅用于资料转换。  
**基础规则参考：** 拟以凌天翼主持编写的《三国杀官方规则集 v3.0》为初始底本；已保存第三方网页版快照，原件、版本和适用范围仍须核验。  
**项目性质：** 独立研究与开发，不代表游戏官方裁定。

## 1. 为什么做这个项目

《三国杀》的规则体系随版本、武将、模式与运营平台持续扩展。复杂技能交互经常涉及事件时序、效果替换、例外条款与适用范围，仅靠自然语言检索或简单的“技能—效果”关联，难以稳定地解释结算结果。

本项目希望将规则从分散的文本转化为**可追溯、可检查、可讨论、最终可执行**的知识体系。

核心问题是：

1. **规则是什么？** 如何明确描述对象、事件、时机、条件与效果？
2. **规则何时适用？** 多条规则或技能如何依赖、覆盖、修改或排斥彼此？
3. **结论从何而来？** 对具体交互，能否给出推导过程、规则依据，以及尚不确定的部分？

## 2. 目标与非目标

### 长期目标

- **规则知识库：** 统一描述规则概念及其关系，保留来源、版本与适用范围。
- **一致性分析：** 发现规则引用缺失、语义歧义、潜在冲突和无法判定的情况。
- **可解释规则推演：** 在给定游戏状态与操作序列时，展示可能的结算过程及依据。
- **版本比较：** 对不同规则集、模式或平台的差异进行显式记录，不默认它们等价。

### 当前不做

- 不开发完整的《三国杀》游戏客户端或联网对战系统。
- 不在第一阶段实现 NFC、实体卡牌识别或自动化面杀裁判硬件。
- 不一次性录入所有武将、卡牌与历史版本。
- 不预先选定规则引擎的编程语言、数据库、图数据库、DSL、推理框架或用户界面。
- 不把缺乏充分依据的推测包装成官方裁定。

## 3. 基本原则

1. **语义先于实现。** 先澄清规则中有哪些对象、关系、事件和操作，再选择适合的技术。
2. **来源与版本不可省略。** 每项规则或裁定都应能够回溯到具体来源及适用范围。
3. **原文与解释分离。** 区分资料原文、格式转换稿、结构化转写、推导结果和开发者假设。
4. **冲突显式保留。** 未能确定的冲突应标记为“待核实”或“无法判定”，而不是暗中决定优先级。
5. **通过案例检验模型。** 以真实技能交互作为反例和回归测试来源，不以图谱可视化效果代替正确性。
6. **最小化技术承诺。** 优先维护与实现方式无关的知识资产，推迟不可逆的架构决策。

## 4. 资料与证据管理

初始计划使用凌天翼 v3.0 作为基础规则的研究起点，**但在获得并核验完整原件前，不将其具体条款视为已确认事实**。其他官方规则、平台裁定、社区整理与实际游戏行为可以成为补充证据；它们必须保留各自来源身份，不能直接合并成单一“官方规则”。

每条规则记录至少应逐步具备：

| 字段 | 说明 |
| --- | --- |
| 标识符 | 稳定、唯一的规则或概念 ID |
| 来源 | 文档、发布者、链接或馆藏信息、页码／章节等定位信息 |
| 版本范围 | 适用的规则版本、服务器、模式及已知限制 |
| 原始依据 | 可核验的原文定位；必要时记录适量摘录 |
| 语义描述 | 将条款转写为结构化、无歧义的描述 |
| 关联关系 | 引用、依赖、例外、替换、优先级或冲突等关系 |
| 确认状态 | 已核实、待核实、存在争议、已废止等 |
| 验证案例 | 支持或反驳当前解释的具体场景 |

现有资料登记在 [source/index.md](source/index.md)。HTML 和 Markdown 资料均保留在 Git 跟踪范围内，不加入忽略规则。资料的著作权及再分发授权状态另行登记；纳入版本管理不代表已经取得公开再分发授权。

## 5. 待研究的基础语义

以下只是候选概念，并非已经冻结的数据模型：

- **对象与状态：** 玩家、角色、卡牌、区域、标记、体力及其他状态。
- **时间与流程：** 回合、阶段、时机、结算步骤、事件顺序。
- **规则与动作：** 条件、代价、效果、限制、许可、替换、阻止、触发。
- **规则间关系：** 定义、引用、前置依赖、优先适用、例外、覆盖与冲突。

必须重点验证的区别包括“受到伤害”和“失去体力”等概念。它们可能在最终数值上表现相似，但所涉及的事件、触发窗口和后续效果并不一定相同。最终定义应由资料和案例共同约束。

术语与候选定义记录在 [docs/glossary.md](docs/glossary.md)。

## 6. 工作方法

1. **资料登记：** 核验原件、记录来源和版本，不急于改写规则。
2. **术语梳理：** 从基础条款提取术语、定义与相互依赖。
3. **语义建模：** 为对象、事件、条件、效果和时序提出可检查的表示方式。
4. **案例检验：** 选择少量具有代表性的技能交互，尝试推演并记录失败原因。
5. **迭代修订：** 区分“资料不足”“规则自身存在歧义”和“模型表达能力不足”。

一项结算结果只有在**依据、适用版本和推导步骤**可被审查时，才算通过验证。

建模决策的记录规范见 [docs/decisions/README.md](docs/decisions/README.md)，案例记录规范见 [cases/README.md](cases/README.md)。

## 7. 项目目录与资料工具

```text
Sanguosha/
├── README.md                       # 项目目标、边界与原则
├── .gitignore                      # 环境和临时文件；不忽略资料
├── environment.yml                 # 资料转换用 Conda 环境
├── docs/
│   ├── glossary.md                 # 术语与候选定义（尚未冻结）
│   └── decisions/
│       └── README.md               # 建模决策记录规范
├── source/
│   ├── index.md                    # 来源登记与版本核验状态
│   └── original_rules/
│       ├── html/                   # 只读网页快照及配套资源
│       │   ├── index.html          # 网页入口
│       │   ├── manifest.json       # 来源 URL、大小及 SHA-256 清单
│       │   └── …                   # 其余规则页面、搜索索引、图片等
│       └── md/                     # 对应的 Markdown 格式转换稿
│           ├── index.md            # 首页转写
│           └── …                   # 按原站目录组织的其余转写
├── cases/
│   └── README.md                   # 规则交互案例记录规范
└── scripts/
    └── html_to_markdown.py         # HTML 正文转换工具
```

`source/` 使用单数命名；`original_rules/` 是现有规则资料的归档目录名，不表示其官方身份已经核验。未来是否增加 `rules/`、`schemas/`、`engine/`、`tests/` 等目录，取决于语义模型与实验结果。

### 资料转换环境

```bash
conda env create -f environment.yml
conda activate sanguosha
python scripts/html_to_markdown.py
```

现有环境名为 `sanguosha`，使用 Python 3.12 和 `markdownify`。已有该环境时直接激活即可。脚本位置保持在 `scripts/`，读取 `source/original_rules/html/`，重新生成 `source/original_rules/md/`。Markdown 保留正文结构及图片引用，站内页面链接改为对应 `.md` 文件；图片仍引用 HTML 快照中的资源。转换产物不是已经核验的语义模型，逐条正文一致性复核仍待完成。

### 浏览原始快照

```bash
conda activate sanguosha
python -m http.server 8000 --directory source/original_rules/html
```

随后访问 <http://localhost:8000/>。也可直接打开 `source/original_rules/html/index.html`，但搜索索引需要通过 HTTP 加载。

当前本地 HTML 快照已设为只读。Git 不保存普通文件的只读权限，重新检出后如需恢复相同保护，可执行 `chmod -R a-w source/original_rules/html`。

## 9. 当前开放问题

- 凌天翼 v3.0 完整原件、出版／发布信息及实际适用范围是什么？
- 已保存的第三方网页版与完整原件是否一致，是否存在遗漏或后续修订？
- 哪些概念应当是独立实体，哪些只是属性、关系或过程？
- 如何描述事件窗口、结算顺序、效果替换及优先级？
- 同一规则在不同平台或历史时期的差异应如何表示？
- 如何区分规则自身矛盾、资料不足与模型表达不足？
- 什么样的案例足以证明第一版模型具备实用价值？

## 10. 项目状态

当前为**初始化阶段**：基础目录和记录规范已建立，已归档 55 个 HTML 页面及其 Markdown 转换稿。网页下载覆盖范围和文件校验信息见来源登记；完整原件、官方发布身份、适用范围及正文转写一致性尚未完成核验。尚无已确认的术语模型、推演结论或已验证的交互案例。

任何未核实的规则说明、尚未验证的推导和拟议中的模型设计，都不应被视为已确立的规则事实。

后续优先事项：**核验规则原件 → 建立基础术语表 → 选择首批交互案例 → 形成最小语义模型。**
