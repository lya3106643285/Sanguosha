# 三国杀规则引擎基础语义设计

**版本：V0.1 Draft**  
**阶段：基础骨架探索**  
**规则依据：《三国杀官方规则集 3.0》**

## 0. 设计目标

建立一套高度统一、可递归组合、可动态改变执行结构的规则表达与执行体系。

本项目不以针对具体武将、卡牌及技能编写大量独立的处理逻辑为目标，而是试图从三国杀的规则体系中提取有限的基础抽象与原子操作，使复杂规则能够通过基础结构的组合得到表达。

在理想情况下，引擎内核无需理解「杀」「伤害」「武将」「回合」等具体游戏概念。这些概念应当由规则层定义，而非作为内核中的特殊机制存在。

本阶段仅讨论语义模型，不预设编程语言、存储方式、知识表示技术或具体数据结构。

---

## 1. 基本设计原则

### 1.1 一切规则行为皆事件

事件（Event）是规则行为的基本表达单位。

游戏开始、回合执行、阶段执行、牌的使用、伤害结算、技能发动、属性求值等，原则上均通过事件表达。

不同事件之间的区别应当主要来自其内部结构、属性、条件和执行内容，而非不同的底层执行机制。

### 1.2 一切事件皆值

事件本身是一种具有明确结构与执行语义的值（Value）。

事件与数值、集合、序列等数据在管理层面具有同等地位，能够通过统一的操作进行创建、存储、读取、引用和组合。

事件可以作为其他事件的属性、子事件、输入或输出，也可以成为操作的作用对象。

事件具有执行语义，但并不因此脱离统一的值空间。

### 1.3 数据不可变

已经产生的数据不得被直接修改。

任何数据变化都通过生成新的值，并改变相应的引用关系实现。

该原则同样适用于：

- 普通数值；
- 集合与序列；
- 事件及其内部属性；
- 条件与钩子；
- 事件执行结构。

因此，事件的动态变化并不意味着对既有事件值的直接修改，而意味着产生新的事件版本。

### 1.4 操作具有原子性

操作（Operation）是规则执行体系中不可再分解的最小动作。

操作本身不具有规则插入时机，执行期间不允许其他规则事件插入。

此处的原子性是规则语义上的原子性，而非计算机指令级别的原子性。

一个操作可以同时改变多个引用关系，只要规则不允许其中间状态被独立响应或观察。

### 1.5 持续性效果通过条件表达

不引入为了维持某种效果而持续运行的事件。

持续性规则效果通过条件、钩子及相关数据表达。当相应事件发生且条件成立时，规则效果参与该事件的结算或求值。

持续存在的是规则定义及其有效条件，而不是事件的执行过程。

---

## 2. 统一值空间

系统中的所有数据均属于统一的值空间。

值可以是简单值，也可以是由其他值及引用构成的复合值。

候选值类型包括：

| 值类型 | 示例 |
|---|---|
| 数值 | 体力、点数、伤害值 |
| 逻辑值 | 合法、不合法 |
| 标识 | 角色身份、实体牌身份 |
| 引用 | 对其他值的访问关系 |
| 集合 | 手牌集合、目标集合 |
| 序列 | 回合顺序、结算顺序 |
| 事件 | 摸牌、伤害、距离计算 |
| 操作描述 | 读取、绑定、插入 |
| 条件 | 技能有效条件、发动限制 |

以上类型仅为语义分类，不意味着必须建立相应的独立存储或管理系统。

事件同样可以由上述任意类型的值构成。

---

## 3. 事件模型

### 3.1 事件结构

一个事件原则上包含以下内容：

- **属性**：描述事件的身份、参数、上下文及相关信息。
- **条件**：描述事件成立、执行或插入所需满足的约束。
- **执行结构**：由有序的子事件与原子操作构成。
- **时机接口**：描述其他事件能够参与其执行的位置。
- **结果**：事件执行或求值所产生的值。

概念结构如下：

    Event
    ├── Attributes
    ├── Conditions
    ├── Sequence
    │   ├── Event
    │   ├── Operation
    │   ├── Event
    │   └── ...
    ├── Timings
    └── Result

事件结构是递归的，操作则构成递归执行的终点。

### 3.2 事件的递归性

一个事件可以包含其他完整事件。

例如：

    游戏事件
    └── 回合事件
        └── 出牌阶段事件
            └── 使用牌事件
                └── 伤害事件
                    └── 扣减体力事件
                        └── 濒死事件

上述结构仅用于说明递归关系，不限定具体的规则结算顺序。

游戏、回合、阶段、技能与属性求值应当尽可能共享同一种事件抽象。

### 3.3 事件的身份与版本

由于事件本身是不可变值，需要区分：

- 事件的定义；
- 某一次实际发生的事件；
- 该事件在执行过程中的不同版本。

同一个事件定义可以被多次执行。每次执行应具有可区分的身份。

事件执行过程中产生新的属性值或执行序列时，可以建立新的事件版本，而不改变此次事件的逻辑身份。

具体身份与版本管理机制暂未确定。

---

## 4. 属性模型

属性不应仅被理解为静态字段，而应当具有统一的求值语义。

规则层的属性获取原则上可以表示为子事件，其结果可以是普通数值、引用、集合，乃至另一个事件。

### 4.1 简单属性

例如读取实体牌的原始点数：

    获取原始点数事件
    └── 读取已存储的值
        → 7

### 4.2 复合属性

例如获取角色间的有效距离：

    距离求值事件
    ├── 计算基础距离
    ├── 处理适用的距离修正规则
    └── 返回最终距离

### 4.3 可干预属性

例如确定一次伤害的数值：

    伤害数值确定事件
    ├── 获取初始伤害值
    ├── 处理合法的数值修正
    └── 返回最终伤害值

简单属性与复合属性共享统一的访问语义，而不要求具有完全相同的内部实现。

需要注意，属性求值的内部接口不必然构成规则集规定的玩家响应时机。不能因为属性被事件化，就产生额外的技能发动机会。

属性的求值时间、结果有效范围及是否允许重新求值，仍须由具体规则确定。

---

## 5. 操作模型

操作是事件最终执行的基础动作。

操作不具有独立的规则插入时机，也不需要通过另一个事件解释其内部执行过程。

当前考虑的候选操作包括：

| 操作 | 语义 |
|---|---|
| Create | 创建新的不可变值 |
| Read | 读取值 |
| Bind | 建立或更新当前引用关系 |
| Compute | 根据输入产生计算结果 |
| Insert | 向执行序列中插入事件 |
| Remove | 从待执行结构中移除元素 |
| Replace | 替换指定位置对应的值 |

这不是已经确定的最小操作集合。

其中，Insert、Remove、Replace 等操作可能并非独立的底层原语，而可以进一步归约为新值的创建及引用关系的更新。

操作的最小完备集需要通过规则集分析进一步确定。

---

## 6. 状态与引用

### 6.1 状态更新

游戏状态由当前有效的引用关系及其指向的值共同决定。

以角色体力变化为例：

    初始：
        V0 = 4
        HP → V0

    扣减两点体力：
        V1 = 2
        HP → V1

    回复一点体力：
        V2 = 3
        HP → V2

V0、V1、V2 均为不可变值。

体力发生变化时，不修改旧值，而是产生新值并建立新的绑定关系。

### 6.2 身份与状态分离

一个对象的身份不应随其状态变化而变化。

例如，实体牌从手牌区移动到弃牌堆时：

- 实体牌身份保持不变；
- 区域状态产生新的值；
- 当前有效的区域引用发生变化。

角色、实体牌、技能等概念均需要具备可稳定引用的身份，但不因此成为持续运行的事件。

### 6.3 引用的历史版本

如果引用关系本身也属于不可变数据，那么引用更新同样可以通过产生新的绑定版本实现。

系统在任一时刻具有一个当前有效状态，但此前的状态及引用关系在语义上仍然成立于其对应的历史时刻。

历史版本是否全部保留、如何索引与回收，属于后续实现问题。

---

## 7. 执行序列与插入

### 7.1 有序嵌套结构

事件内部具有有序执行结构，结构中的元素可以是事件，也可以是操作。

执行结构允许递归嵌套。

链表是目前用于理解这一结构的概念模型，而非已经确定的物理存储结构。

### 7.2 插入

插入是三国杀规则执行中的核心操作之一。

当某个事件满足合法插入条件时，可以进入相应的执行位置，参与后续结算。

由于执行序列本身也是值，插入可以通过序列版本更新表达：

    S0 = [A, B, C]

    插入事件 X：

    S1 = [A, B, X, C]

    Sequence → S1

原序列 S0 不发生改变。

### 7.3 执行结构与数值的统一管理

修改伤害值与插入事件，在数据管理层面不存在本质区别。

| 行为 | 原值 | 新值 |
|---|---|---|
| 修改伤害值 | 1 | 2 |
| 插入事件 | [A, B, C] | [A, B, X, C] |
| 修改目标集合 | [A] | [A, B] |
| 修改事件属性 | Event V0 | Event V1 |

上述行为均可以通过创建新值并更新有效引用实现。

因此，游戏状态变化与规则执行结构变化可以共享相同的管理机制。

---

## 8. 时机、条件与钩子

### 8.1 时机

时机用于描述事件能够被合法插入的条件与位置。

事件具有承载其他事件插入的结构能力，但并非所有结构位置都构成合法时机。

具体插入权限由规则定义。

### 8.2 条件

条件描述某种规则关系是否成立。

例如：

- 角色是否拥有某技能；
- 当前事件是否属于指定回合；
- 某个技能是否达到发动次数限制；
- 某张牌是否满足规定的属性要求。

条件自身可以作为值进行存储、引用和组合，其判断过程可以通过事件表达。

### 8.3 钩子

钩子用于将条件、执行位置与待插入事件关联起来。

概念结构如下：

    Hook
    ├── 匹配位置
    ├── 生效条件
    ├── 待插入事件
    └── 插入约束

具有持续效果的技能可以由钩子及其生效条件表达，而无需创建持续运行的事件。

需要区分引擎内部的求值钩子与规则文本中的发动时机。二者可以共享实现机制，但不应被直接认定为具有相同的游戏语义。

---

## 9. 技能模型

技能不应当拥有一套完全独立于其他规则概念的执行体系。

技能的执行内容可以由事件表达，技能的有效性由相关状态与条件描述。

例如，状态类技能可以表示为：

    马术
    ├── 条件：技能有效
    ├── 钩子：对应的距离求值位置
    └── 距离修正事件
        └── 产生修正后的距离值

非状态类技能可以表示为：

    技能
    ├── 条件：满足发动要求
    ├── 钩子：合法发动时机
    └── 技能结算事件
        ├── 选择事件
        ├── 代价事件
        └── 效果事件

二者可以在统一事件模型下获得表达，但仍须保留规则集对不同技能类型规定的语义差异。

---

## 10. 解释与执行

事件作为值存在，并不意味着事件会自行执行。

系统需要一个基础解释机制，负责：

- 解释事件及操作的结构；
- 推进当前执行位置；
- 判断并处理合法插入；
- 调用原子操作；
- 更新当前有效引用；
- 获取并传递事件结果。

解释机制不应负责理解具体卡牌或技能的游戏含义。

当前执行位置、事件版本及结算结果同样可以作为值进行管理。

基础解释机制构成整个递归规则体系的执行边界。

---

## 11. 历史与因果关系

由于数据及事件值具有不可变性，系统具备建立完整规则因果关系的基础。

一个结果可以关联产生该结果的事件，一个事件也可以关联其依赖的输入值、子事件以及所产生的输出。

因此，系统可以形成两种相互关联的结构：

- **执行结构**：描述事件以何种顺序、何种嵌套关系发生。
- **因果结构**：描述事件与数据之间的产生、依赖和修改关系。

前者用于推进游戏，后者可以用于规则解释、争议追溯、调试及历史重建。

二者应当共享同一套事件与值管理机制，而不是分别维护两套互不关联的事实。

---

## 12. 尚未解决的问题

当前模型仍有以下待研究的问题：

1. 原子操作的最小完备集。
2. 事件属性的求值、缓存与重新求值规则。
3. 引用、对象身份与历史版本的形式化定义。
4. 事件插入后，执行位置的更新与恢复机制。
5. 多个事件竞争同一插入位置时的顺序确定。
6. 事件取消、中止、跳过与作用域失效的表达。
7. 条件求值及事件递归过程中的循环依赖。
8. 同时发生的多项状态变化的原子提交。
9. 状态类技能是否均能通过条件与钩子获得完整表达。
10. 当前模型能否覆盖规则集中的所有基础概念，而不引入大量特殊机制。

这些问题不应在缺少规则依据时过早确定实现方案。

后续应通过规则集中的具体流程、边界案例及复杂技能交互验证本模型，并根据反例调整基础抽象。

---

## 13. 当前设计的核心概括

**一切规则行为皆事件。**

**一切事件皆值。**

**一切已产生的值皆不可变。**

**一切状态变化皆可通过新值与引用关系表达。**

**一切事件执行最终归约为原子操作。**

本项目所追求的不是为三国杀的全部规则编写对应的处理程序，而是建立一个足以表达这些规则的统一语义系统。
